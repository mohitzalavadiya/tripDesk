# TripDesk — Production Deployment Runbook

This document provides a production deployment guide for the **TripDesk Multi-Tenant Travel Agency SaaS Platform**.

---

## 1. Architecture Overview & Core Invariants

TripDesk is built on Next.js (App Router), PostgreSQL (Supabase), Prisma ORM, and Supabase Auth.

### Authoritative Architecture Invariants:
1. **Exactly Two Internal System Roles**:
   - `PLATFORM_OWNER`: Super admin who oversees the SaaS platform, monitors all agencies, manages plans/subscriptions, broadcasts system notices, and reviews SaaS audit logs. Exactly one Platform Owner with `agencyId = null`.
   - `AGENCY_OWNER`: Travel agency principal who manages their specific agency, customers, trips, quotations, bookings, vouchers, supplier ledgers, and staff operations.
   - **NO Customer Internal User Accounts**: Customers are external business records and access their itineraries, quotations, and vouchers via secure UUID and cryptographic access tokens.
2. **Financial Distinction**:
   - **Platform SaaS Subscription Revenue**: Revenue generated by TripDesk from agency subscriptions.
   - **Agency Customer Booking GMV**: Commercial gross merchandise value and supplier costs managed by individual agencies. These numbers are never mixed.
3. **Multi-Tenant Data Isolation**:
   - Every agency query enforces `where: { agencyId }` resolved strictly from the server-side session.
   - Platform Owner views aggregate telemetry across tenants without leaking data between agencies.

## 4. Database Setup & Migration Strategy

### Initial Database Deployment
1. Verify Supabase project is active and connection strings are accessible.
2. Synchronize the complete schema to the database:
   ```bash
   npx prisma generate
   npx prisma db push
   ```
3. Initialize the singleton Platform Owner account:
   ```bash
   npm run bootstrap:owner
   ```
4. (Optional) Initialize default SaaS subscription plans:
   ```bash
   npx tsx prisma/seed.ts
   ```

### Zero-Downtime Migration Policy for Future Releases
- All schema additions must be backward-compatible (nullable columns or sensible defaults).
- Never rename or drop columns in a single deployment; follow the **Expand and Contract** pattern:
  1. **Phase 1 (Expand)**: Add the new column as nullable, deploy code that writes to both old and new columns.
  2. **Phase 2 (Backfill)**: Run data migration script to populate new column from old column.
  3. **Phase 3 (Contract)**: Update code to read exclusively from the new column, make column non-null, and deprecate old column.

## 5. Build & Deployment Steps

### Vercel Deployment (Recommended)
1. Link GitHub repository to Vercel.
2. Set Framework Preset to **Next.js**.
3. Set Build Command: `prisma generate && next build`.
4. Set Output Directory: `.next`.
5. Populate all Environment Variables in Vercel Project Settings.
6. Deploy production branch.

### Docker / Self-Hosted Deployment
```dockerfile
FROM node:20-alpine AS base
WORKDIR /app
RUN apk add --no-cache libc6-compat openssl
COPY package*.json ./
COPY prisma ./prisma/
RUN npm ci
RUN npx prisma generate

COPY . .
ENV NODE_ENV=production
RUN npm run build

EXPOSE 3001
ENV PORT=3001
CMD ["npm", "run", "start"]
```

## 6. Background Schedulers & Cron Setup

To execute automated payment reminders, upcoming trip alerts, and customer feedback sweeps, configure a recurring HTTP cron task (e.g. Vercel Cron, Supabase `pg_cron`, or Cloudflare Workers):

- **Schedule**: Every 1 hour (or daily at 08:00 UTC)
- **Endpoint**: `POST https://app.tripdesk.io/api/communication/automation/run`
- **Headers**:
  ```http
  Authorization: Bearer <CRON_SECRET>
  Content-Type: application/json
  ```
- **Body**:
  ```json
  { "scope": "all" }
  ```

## 7. Backup, Disaster Recovery & Rollback

### Database Backups
- Supabase automatically creates daily point-in-time recovery (PITR) backups on Pro tiers.
- For offsite backups, schedule a daily `pg_dump`:
  ```bash
  pg_dump "$DIRECT_URL" --format=custom --file=tripdesk_backup_$(date +%Y%m%d).dump
  ```

### Rollback Procedure
1. **Application Rollback**:
   - In Vercel, navigate to Deployments and click **Instant Rollback** to the prior stable deployment ID.
2. **Database Rollback**:
   - Because schema changes are strictly additive and backward-compatible, rolling back application code will not break existing database state.
   - If an emergency database restore is required, use Supabase Point-In-Time-Recovery to restore to the timestamp immediately prior to deployment.
